# Hook 成卡：Path A 还是 Path B 先做——决策简报

- 日期：2026-11-05（晚）；依据：Hook 审计报告 `reports/knowbase-hook-capture-audit.md`（基线 e8ab132，§八增量复核至 5d064ad）
- 待决问题（主会话 2026-11-05 19:08 已问出，尚未答复）：P0 第一项 Hook 时识别与成卡，先做 Path A 还是 Path B？
- 结论先行：**先做 Path B，再做 Path A。不是二选一，是先后顺序——两条路收敛到同一个 Knowbase 侧成卡端点（校验 → 查重/复用判断 → 新卡或增量更新），B 先把这个端点建起来，A 之后只是多一个调用方。**

## 两条路的现状（审计已核实）

| | Path A：宿主主动提交结构化候选 | Path B：Hook 事件 + 本地规则过滤 + 小范围模型调用 |
|---|---|---|
| 现状 | **协议不存在**。`memory_save` 是自由格式直接写（`server.py:107` → `writer.create`），不走结构化候选校验；`memory_job_*` 是执行器协议，不是宿主上报协议（审计 §一、P2-10） | **地基已有一半**。确定性噪声过滤（`hook_policy.py`）、检查点（stop / before-compact，或 6 个工具事件 / 10 分钟，`host_events.py:346`）、增量游标 + `text_hash` 去重、片段 ≤4000 字符（`materials.py:67`）都已存在；缺的是检查点上的一次小范围模型调用 + 复用判断 + 成卡 |
| 谁做识别 | 宿主模型（已在上下文中，不用重读会话） | Knowbase 侧模型（只看已过滤的小范围片段，不读全会话） |
| 依赖 | 每个宿主都要采纳统一 Skill/协议。用户在用 ZCode（主力）、Claude Code、Codex、opencode、Cursor、Trae，逐宿主落地的工作量在 Knowbase 仓库之外 | 只在 Knowbase 仓库内改动，不依赖任何宿主配合 |
| 成本 | 宿主侧少量 Token（上报本身）；Knowbase 侧零新增模型调用 | 每批有价值事件一次模型调用；但已有硬 cap：日调用 20 次、日输入 512k 字符、单批输入 128k（`config.py:105-106`，审计 §三）——B 的调用量必须先算进这个预算，否则很快打满 |

## 为什么 B 先

1. **B 不依赖外部配合，可独立交付验证。** A 的成败取决于宿主是否按协议上报；B 在沙箱 + 一台 Mac 上就能跑通、测准。
2. **A 需要的 Knowbase 侧能力，B 也要建，且是同一份。** 无论候选来自宿主还是来自 Hook 模型调用，Knowbase 都要做：确认知识成立 + 必要证据、检索已有卡判重复/补充/全新、新卡创建或已有卡增量更新、保存任务与使用关系（用户 2026-11-05 设计 §二的 4 步）。先做 B 等于先把这 4 步的服务端做出来；A 随后只需加一个"宿主提交结构化候选"的入口，复用同一套校验与查重。
3. **B 直接复用已有管线，改动面最小。** 检查点 → `capture_increment` → 建批相似快照（`wide_recall` 前 10 张卡已附在批次上，`materials.py:135`）这条线今天已经通了，只是终点是 worker 提炼而不是 Hook 时成卡。

## B 先做也绕不开的两个硬点（两条路共有，别指望换路解决）

- **复用/更新没有自动出口。** 自动执行器被明文禁止 `update` / `link_existing`（`executor.py:322-323`），重复只能进 review；写入层唯一防线是标题相似度 0.82，命中即报错（`commit_adapter.py:198`）。P0-1（成卡）与 P0-2（复用判断）必须同一批做，否则 B 造出来的还是重复卡。第一批的验收标准应写明：重复 → 链接/更新旧卡（或明确进 review 的条件），而不是只做到"能成卡"。
- **选 A 还是 B 都不解锁 verified 晋升。** V2-01 两道晋升门默认仍关，生产观测任务键保留 `unknown:` 前缀、不计独立性（审计 §八）；晋升要等任务身份设计（V2-09 未决）。Hook 时成的卡先落 `once` / staging，这是预期内的，不是 B 的缺陷。

## 建议的第一批切分（B）

1. 检查点触发时（沿用现有检查点条件），对已过滤片段跑已有卡检索（复用 `wide_recall` 的相似快照逻辑），判重复 / 补充 / 全新。
2. 只把有价值的当前事件 + 相似卡摘要送模型（全会话输入默认禁止，用户设计 §四），产出小型结构化候选，走现有 `materialize.submit` 的 `duplicate_evaluation` 门。
3. 用内部轻量队列做短时处理，不阻塞宿主（用户设计 §二）；日调用预算内先跑，超预算进 `retry_wait` 而不是静默丢（沿用 `distillation.py:183-195` 的已有语义）。
4. 验收：一次会话结束时卡已在（不再等 worker 60 秒 + 提炼链路）；重复内容不产生新卡；`quarantine` 与 `verified` 规则不动。

## Path A 的后续位置

B 的服务端（校验/查重/成卡端点 + `duplicate_evaluation` 门）跑通后，A 的工作收敛为：定一个结构化候选协议（字段、证据要求、版本号约定）+ 让宿主 Skill 按协议提交 + 复用 B 的端点。那时 A 的价值才可衡量：宿主已在上下文中识别，Knowbase 侧可以省掉 B 的那次模型调用。
