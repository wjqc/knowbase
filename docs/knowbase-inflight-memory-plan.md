## 1. 用户结果与约束

目标：用户发出一次长任务后，即使不再发消息，Agent 在进入具体子任务、发现新问题和得到验证结论时，仍能查经验、采用经验、及时沉淀；上下文压缩或进程退出不丢掉尚未整理的证据。

使用率以“该查时查了、相关知识影响了实际行动、值得复用的结论得到处理”为准，不能用增加无效查询、卡片数量或反馈数量达成。

沿用既有设计：Hook 收集事件、轻量检索和递送提醒；当前宿主 Agent 负责理解任务、拆查询、判断适用性和总结；MCP 负责检索、任务状态与写入。knowbase 不新增独立模型服务，不读取宿主密钥。无需新界面，F1–F5 本期不适用。

| 用户任务 | 输入和必要条件 | 合格结果 | 不算完成 |
|---|---|---|---|
| 执行长方案 | 可读取的方案、项目 scope、当前子任务 | 当前子任务执行前获得相关约束；后续子任务到达时继续检索 | 整篇原文只查一次；只检索开头几段 |
| 执行中遇错 | 工具实际结果、错误签名、环境 | 下一次相关尝试前补查经验，核对适用条件 | 错误入队后无人消费；只到下一条用户消息才查询 |
| 阶段经验沉淀 | 现象、行动、实际验证、来源片段 | 候选经查重保存或明确无候选，下一任务可检索 | 只生成摘要；入队当保存成功；把未实施方案写成验证经验 |
| 长会话恢复 | 原始片段快照、覆盖清单、持久游标 | 只补未处理部分，重复执行不重复写卡 | 已有一次 save 后忽略剩余会话 |

## 2. 当前事实与缺口

以下是当前源码静态取证，不是运行验收：

- `hooks.py:user_prompt` 在用户消息时检索，直接以原始 prompt 搜索；没有按实施阶段构建查询计划。
- `_maybe_trigger_mid_session_capture` 从 `cmd_user_prompt` 调用：仍需下一次用户输入；`mid_session_capture` 默认 false，flag 每个会话最多触发一次。仅开启此开关无法覆盖持续执行。
- `stop_event` 仍以会话是否有过 memory_write 判断漏存；一次 save/update/feedback 可能遮蔽后续尚未沉淀的内容。
- 已有 `memory_capture → memory_job_claim/renew/submit/status`、jobs 租约和 checkpoint 构建，可复用，不能再建第二套提炼队列。
- `normalizer.py` 对单事件文本保留到 8,000 字符，部分工具结果更短；`capture_impl` 调用单个 `build_checkpoint`，默认预算 16,000 字符；claim 返回材料还可能被 `max_chars` 截断。需要补齐原文分页和覆盖证明，不能仅把预算调大。
- 截图和当前配置只确认 SessionStart/UserPromptSubmit/Stop。执行中工具事件、压缩前事件的支持、参数和上下文注入时机，须逐宿主实测，不能把候选事件名直接写成已接通。

## 3. 执行中使用路径

```text
用户长输入/方案文件
  → 当前 Agent 提取目标、约束、子任务、风险、待确认项
  → 保存任务主题及原文定位，按当前阶段制定短查询
  → 进入子任务前检索 → 读相关卡 → 核验条件 → 影响行动
  → 工具结果出现新错误/新对象 → 补查 → 验证解决方案
  → 阶段完成 → 从新增证据提炼 → 查重 → 保存/更新/待审核
  → 进入下一子任务；压缩和结束仅作最后兜底
```

### 3.1 两条互补的触发路径

**宿主主动路径（所有能调用 MCP 的宿主均可接入，但执行纪律仍需验证）**：在工作流中要求 Agent 进入子任务、发现新问题、阶段完成时调用下文的 `memory_context`。这是 Agent 在本轮执行中的工具调用，不依赖新用户消息。SessionStart 只负责一次性下发协议和恢复待办；不能承担全过程执行。

**工具事件路径（按宿主能力启用）**：如宿主确实提供执行前后工具事件，适配器观察即将访问的模块、实际错误和阶段变化；事件名称、是否支持继续执行、能否注入到下一步，均以该宿主录制样本为准。事件只做确定性处理，语义查询计划仍由当前 Agent 提交。支持压缩前事件时额外保存游标和待沉淀证据；不支持时由主动路径在宿主公开的整理节点执行，不承诺能截获任意自动压缩。

无执行中事件的宿主标记 `assisted`，不能声称达到强制自动覆盖。MCP 服务不能自行监听模型思考、任意聊天或唤醒已退出的 Agent。仅靠轮询 transcript 可收集、入队，不能证明宿主会读取并完成总结。

### 3.2 触发策略

| 时机 | 检索动作 | 沉淀动作 |
|---|---|---|
| 长任务拆解后 | 查当前目标和高风险约束，建立主题清单 | 原文和方案先作材料，不直接生成“成功经验” |
| 进入新子任务/新模块/新环境 | 按本阶段问题、实体和已知限制查询 | 将上一阶段未处理证据保留到 checkpoint |
| 新错误、失败测试、意外行为 | 用错误签名、组件名、环境补查，再决定下一次尝试 | 记录现象和尝试，解决前不当结论保存 |
| 准备重要方案选择 | 查历史决策、约束和相邻反例 | 已确认的决定可提炼 decision，注明尚未实施部分 |
| 阶段验证完成、用户纠正 | 按需查重、核对旧卡 | 整理本阶段增量，调用既有 capture/job 流程 |
| 长时间持续操作 | 有新实体或未解决问题才补查 | 达到阈值后的下一工具事件检查证据是否值得提炼 |
| 压缩前/Stop | 恢复未覆盖主题，不反复全库查询 | 保存未处理片段和游标，兜底处理待办 |

初始可调默认：6 次非 knowbase 工具操作或 10 分钟后，在下一个事件检查是否需要 checkpoint；新错误/阶段完成立即检查，不等待阈值。阈值仅是防遗漏兜底，不能替代语义判断，不是已测最优参数。

排除 knowbase 自身调用、其 Git 同步和遥测操作，防止“检索触发检索、保存触发保存”。相同错误在环境未变时只补查一次；普通读取同模块和重复运行相同工具不机械重复检索。

### 3.3 现有工具可以先执行的宿主规则

以下规则可先作为工作流指引使用，不依赖拟新增工具；本轮仅提供模板，尚未写入实际 Agent 配置。它能改善主动使用，但不能代替工具事件的真实接线验收。

```text
1. 接到长任务，先列目标、约束和子任务；为当前子任务构造具体查询，
   调用 memory_search（显式 scope），必要时 memory_read 核对适用条件。
2. 在本轮连续执行中，每次开始新的子任务/模块，或出现新的实际错误，
   重新判断并检索相关知识；不要等待用户下一条输入，也不要整篇原文只查一次。
3. 知识命中只作候选。已参考的卡记录版本和用途，实际验证后如实反馈。
4. 一个问题解决且验证、一个阶段完成时，判断是否形成可复用结论。
   有结论就先查重，再按既有治理要求 save/update；材料较多时按有界增量
   调用 memory_capture，随后 claim/submit/status 完成提炼，不把 queued 当已保存。
5. 当前 capture 长文本完整性未修复前，仅传入已确认完整的有界片段，
   在宿主工作记录保存尚未传入的片段与原文位置，后续分批处理，禁止只传摘要冒充全部原文。
6. 完成一次保存后继续跟踪后续新经验；没有可复用内容允许不保存。
   结束/整理上下文前核对所有阶段的覆盖与待办，未完成任务明确保留。
```

## 4. 长方案和长输入怎么查

### 4.1 先结构化，再分阶段查询

由正在执行任务的宿主模型生成：目标、明确约束、子任务、涉及的系统/代码实体、风险、原文位置、待确认项。任务主题须覆盖输入的全部章节/语义段，当前不执行的内容标 pending，不能当成已经查过。

查询表达“现在要解决什么”，而不是整篇复制：`组件/业务实体 + 操作/问题 + 关键环境或限制`。保留错误码、类名、库名等精确词；必要时由宿主作同义改写。短输入“继续”从已有任务状态恢复当前主题，不应单因字数不足放弃。

示例仅用于说明查询构造，不表示库中已有答案。用户提供一份涵盖认证、SSE、侧栏和断线恢复的实施方案：

| 到达阶段 | 可以构造的查询 | 核对内容 |
|---|---|---|
| 开始认证适配 | `旧系统 登录态 token iframe` | 信任边界、历史鉴权限制 |
| 开始 SSE | `SSE 断线重连 会话恢复 重复消息` | 恢复约定及重复消费风险 |
| 开始侧栏 | `侧栏 首次预填 面板挂载` | 既有体验和生命周期约束 |
| 执行中首次 401 | `SSE 401 token 过期` | 新观测到的具体故障 |

将相关候选合并按卡片内容版本去重，返回“结论摘要、适用条件、来源、验证状态、对应子任务”。索引命中不等于已读、已采纳；Agent 需要时再读全文。标注一次候选是否参考、采用、无关或未验证，不自动生成 helpful。

### 4.2 有界查询与覆盖

初始每个活跃子任务最多 3 个查询方向，首次最多 6 次检索；每次最多回传 3 条候选摘要，默认合计注入预算约 800 token。全文另按需读取并记录成本。预算为待实测的默认值；token 估算与实际计量分开。

零命中允许一次有针对性的改写；仍无结果明确“当前无适用记忆”，继续正常源码分析。达到预算后的主题进入 deferred，进入该子任务或取得新证据后再查，不能静默丢弃。大输入沿原文章节/段落分页，超出单次预算返回 next_cursor、未处理片段数与完整性标志。

缓存键含 scope、主题/实体/错误签名、知识版本及相关环境；版本变化或新证据使缓存失效。限频只跳过相同条件下的重复工作，不拦截新的错误和未覆盖子任务。

主动检索可发现 once 候选，但必须标明待验证并由 Agent 核验；自动建议继续保持 verified 门槛。staging、stale、冲突卡仅用于明确的复核/查重，不作执行建议。scope 必须由显式参数、会话绑定或路径映射确定；无法解析时报告缺口，不退化成跨项目全库搜索。

## 5. 执行中怎么总结和入库

### 5.1 以结论和证据为单位

每个阶段保存本地工作记录：问题、实际观察、尝试过的方法、成功/失败结果、版本环境、来源事件/代码位置、验证证据、未知项。只收可观察消息和工具结果，不要求或保存模型隐含思考链。

解决一个问题并取得证据后即可提炼，不等整个实施方案结束。业务知识也必须在需求澄清、方案评审、用户纠正、代码分析中持续识别，不要求先发生故障或完成代码实现。一次输出可以产生多条主题清晰的经验；没有可复用结论时提交 no_candidate 及理由。候选至少保留既有八项小节，不能为凑卡补写证据。

| 输入内容 | 处理方式 |
|---|---|
| 用户提出的未实施方案 | 本地任务材料；已明确决定可作为 decision 候选，验证写“尚未实施” |
| 一次性修改文件列表、进度和通过总数 | 项目进度记录，不入经验卡 |
| 经复现定位的根因及验证过的修复办法 | pitfall/workflow 候选，记录适用和失效边界 |
| 失败尝试 | 作为现象/反例证据；有明确可复用边界时才独立成卡 |
| 用户纠正、业务规则、人员标准、偏好 | 保留出处，遵循现有 staging 人审，不自动生效 |
| 整篇方案或对话原文 | 本地材料快照；明确允许共享的文件才走既有 source 导入，不塞进卡片正文 |

业务规则是重点提炼类别，包括业务术语与对象含义、状态转换、准入/校验条件、角色权限、计算口径、例外处理和跨系统约束。使用既有 bizrule 类型，不再新增平行规则库。每次阶段提炼同时检查“新增技术经验”和“新增/变更业务规则”；用户明确纠正规则时立即形成候选，不等 Stop。

每条规则记录：适用项目/业务对象、触发条件、必须/禁止的结果、例外与边界、原始出处、确认状态、适用版本及未知项；有代码定位时填写 code_refs。可用 Given/When/Then 表达，但不能把未说明的例外补成事实。PRD 条款或用户明确确认可作规则出处，代码逆向仅是候选证据，须写明代码版本及“待业务确认”；仅有 Agent 推测时保留待确认材料，不伪造 provenance 入规则库。

区分规则的业务确认、人工激活和实现验证：已有明确出处的规则可以在尚未开发时保存候选，验证部分注明未实现；Agent 保存 bizrule 仍按现行机制进入 staging，人工 promote 后才供默认检索使用。未激活规则可经显式复核读取，不得冒充已生效知识。规则修订应保留旧版本和变更出处，并提示与旧卡/代码不一致之处，不能直接把现有代码行为视为正确业务规则。

验收增加：一条长需求包含状态规则、权限规则和计算规则，三类均须形成可追溯候选或明确待确认记录；后半段规则不能因文本预算丢失。需求确认但尚未实现、代码与需求冲突、用户纠正旧规则三类样本分别核对确认/激活/实现状态，不用“没有技术踩坑”作为 no_candidate 理由。

### 5.2 增量、去重、恢复

复用 `memory_capture → memory_job_claim → 宿主提炼/查重 → memory_job_submit → memory_job_status`。Hook 入队不是完成；同一会话允许连续多个检查点。移除“本会话已有任意 memory_write 就全部免检”和“每会话仅一次 capture”的覆盖判据。

分别保存 observed（已观察）与 settled（已完成处理）游标；入队时不可推进 settled。处理覆盖以 segment_id/text_hash 为准，状态为 pending/queued/claimed/saved/updated/needs_review/no_candidate；失败和部分处理不跨过未完成片段。后面的片段可独立处理，连续游标只推进到第一个缺口前。

原始事件先在本地持久化，再归一化/切分；禁止截断后把片段标为完整。允许给模型有界摘录，但须保留可读取的完整版本、original_length、truncated、next_cursor 和定位。跨片段的“失败→修复→验证”以事件关联或重叠窗口保持因果；不能把失败误提炼为最终结论。

幂等键包含 host_profile/session_id、scope、原文版本、事件范围/片段哈希和 extractor_version。重试返回同一任务/提交结果；同 key 不同内容拒绝。重复结论优先关联原卡或带 revision 更新，查重包括本项目 once/staging 和允许的 global。提交时复查，旧 revision 和矛盾进入重新评估，不静默覆盖。

只有持久提交并读回确认后，覆盖状态才进入 saved/updated；needs_review 表示候选已处理、知识尚未生效。原文已处理不代表质量已验收。租约、fencing、request_id 继续复用 jobs/commit_adapter；宿主退出后 awaiting_agent，下次由宿主继续，不能声称后台已自动完成。

## 6. 最小接口与数据契约（拟新增）

保留现有 memory_search/read/capture/job/save/update/feedback；新增一个面向阶段的 `memory_context`，共享既有检索和队列，不另造存储服务。以下为设计接口，尚不能调用。

```text
memory_context(
  session_id, event_id, scope, stage,
  task_id, task_revision, current_goal,
  topics=[{topic_id, source_segment_ids, entities, queries, status}],
  evidence_refs=[], observed_cursor="", request_id=""
)
stage = task_plan | subtask_start | new_failure | decision | verified_result
      | checkpoint | before_compact | recover
```

返回字段：`event_id, scope, retrieval_status, candidates[], next_topics[], capture_due, job_ids[], pending_segments, next_cursor, truncated, budget_used, warnings[]`。候选含 `id, revision, summary, applicable_when, confidence, status, topic_ids`；拒绝跨 scope 或缺字段用明确错误。稳定结果状态区分 executed/no_hit/skipped_cache/deferred_budget/scope_unresolved/unsupported_event/failed，失败不得转换成 no_hit。

执行中事件适配器收取 host/tool 的可观察数据，调用同一 context 内核。Hook 无法进行语义拆解时，可用已保存主题/错误关键词作轻量检索，或返回宿主制定查询的指引；不能假设 Hook 子进程能直接借用宿主模型。压缩恢复时返回当前任务主题、采用卡版本、未解决问题和待处理 job 的有界摘要。

在原 memory.db 以幂等迁移新增本地 `context_sessions` 和 `context_events`：

- sessions：host_profile/session_id 主键，scope、task_revision、topics_json、observed_cursor、settled_cursor、coverage_json、last_checkpoint_at、updated_at。
- events：host_profile/session_id/event_id 唯一，trigger、task_id、payload_hash、segment_refs_json、status、reason、job_ids_json、latency_ms、created_at。同事件不同 payload 返回 IDEMPOTENCY_CONFLICT。
- 原文和提炼材料复用 job_spool；过大原文用本地内容寻址对象引用，路径不进入共享卡。仅重建检索索引不能删除以上状态。

锁内仅执行短事务；禁止持 RepoLock/SQLite 写锁等待宿主模型、OCR 或 Git 网络。任务状态与事件完成状态在同库事务关联；跨文件持久化先落不可变对象，再登记引用，启动时对账。队列任务可由原幂等键重领，不能因应答丢失重写卡。

## 7. 宿主接线与边界

| 宿主能力 | 可交付行为 | 上线前必须验证 |
|---|---|---|
| 当前三个 Hook | 规则初始化、用户输入兜底、结束兜底 | 真实输入字段、scope、agent 身份、返回上下文被消费 |
| 工具执行中事件（若支持） | 新阶段/新错误时递送经验及 checkpoint | 用户只发一条任务后，下一次相关行动前确实收到并读到候选 |
| 压缩前事件（若支持） | 保存待办和增量证据 | 压缩后恢复主题/游标，未处理材料能续做 |
| 无工具事件 | 当前宿主主动 MCP 工作流 | 多阶段任务内实际调用；标 assisted，不承诺机械强制 |
| 无活跃宿主 | 保存、解析、排队 | 明确 awaiting_agent，不伪报总结或保存完成 |

先为 ZCode 做一条真实事件能力探针，确认事件规范、工具名前缀、返回注入方式、时机、超时及递归行为；Claude/Trae 各自验证，不能照搬配置。若能力不可用，先交付主动 MCP 工作流和诚实能力标记，不以不存在的 Hook 承诺全自动。

## 8. 性能、安全、观测与恢复

- 同一受信任团队继续本机运行+内网 Git。scope 是相关性边界，不是人员 ACL；环境变量是归因标签，不是认证。
- 来源文字是待分析材料，不能改变工具权限和治理要求。脱敏在共享写入前再执行一次；原始会话默认仅本地，不自动 git add。
- 快速事件路径不做模型推理和网络等待；耗时工作入队。延迟、最大材料体积、查询预算、队列上限均配置化；超限记录 deferred/retry，不截断冒充完整。
- 各事件无论搜索、跳过、失败都记账。分别记录人员/设备/宿主标签，未知值保留 unknown；团队汇总另行只读导出，不将整份数据库加入 Git。
- 指标：应检索阶段中已执行比例、人工标注相关卡召回率、实际采用且已验证的任务数、值得沉淀片段处理率、待办积压/最老年龄、重复候选率、额外延迟和总 token。分母和范围必须注明；查询次数只作诊断。
- feedback 在实际参考/验证后记录，按卡版本+任务结果去重；不因命中/阅读/保存自动 helpful。净 token 和用时收益通过同类任务对照测量。
- 升级前一致性备份 SQLite 和本地对象；增量建表，保留旧日志。新机制独立开关，回滚关闭执行中适配和新工具指引，保留原三 Hook 和现有 MCP；未完成 job 保留可恢复，不删库。

## 9. 验证与实施批次

责任角色：knowbase 维护者负责内核；各宿主接入者负责真实事件探针；团队使用者在试点前标注预期相关卡与可沉淀结论。角色待实际分派，不虚构人员。

| 批次 | 用户结果/落点 | 退出条件和依赖 | 迁移/恢复 | 当前状态 |
|---|---|---|---|---|
| A 能力探针 | `hooks.py`、宿主配置模板、真实录制样本 | 一条用户任务后，工具事件中途递送并被下一步消费；否则转 assisted | 仅隔离配置，保留原接线 | external_pending |
| B 任务驱动检索 | `server.py` 新工具；拟新增 `context.py`；`index.py` 共用检索；工作流规则 | A 确定可用路径；长输入和中途新错均命中预先标注相关卡，实际行动引用版本；无结果正常继续 | 同库增量表；独立开关 | NOT_RUN |
| C 增量沉淀 | `hooks.py`、`adapters/normalizer.py`、`checkpoint.py`、`jobs.py`、`extraction/*` | 两个阶段各产生不同可复用结论均处理；超长证据尾部可读取，重试/崩溃无重复或覆盖缺口 | 备份 spool/游标；租约恢复 | NOT_RUN |
| D 三人真实试点 | README、`docs/trae-rules.md`、宿主指引与只读统计 | 三人各完成一条实际多阶段任务，核对采用结果、候选质量和额外开销，报告宿主差异 | 小批开启，失败关闭新增路径 | external_pending |

独立预期由团队在执行前标注，不以检索系统自己返回的卡作为标准答案。关键反例：

1. 用户只发一次长方案，Agent 连续工作：在第二、第三子任务仍查到所需经验；不得等下一条用户消息。
2. 相关证据位于输入中部和尾部，且超过现有 8,000/16,000 字符：完整定位、查询和提炼，不因头部命中宣布全覆盖。
3. 同一错误反复出现：不重复刷检索；随后换环境/出现新错误必须补查。
4. 已保存阶段一经验后继续阶段二：新增证据仍会处理，feedback 不冒充沉淀完成。
5. 方案声称成功但工具实际失败：不生成已验证经验；业务规则候选仍进 staging。
6. claim 只返回材料前半段：后半段保持 pending，下一批能够领取；不允许 renew 后仍不断返回同一截断内容。
7. 保存成功应答丢失、任务重投、压缩、宿主退出：已有幂等和游标恢复后卡片唯一、覆盖不前移过缺口。
8. scope 缺失、Hook 不支持、队列满、索引失败：分别报告真实状态，不当作“未命中”，不无限阻断开发。
9. memory_context/read/save 及同步自身不递归触发；重复注入不导致 helpful 数虚增。

高风险前置门：A 未验证前不得宣称 ZCode 全自动；真实长文本与分页未过前不得宣称自动总结完整；C 恢复测试未过前不得扩大自动写入。可独立先完善主动检索指引、scope 和日志，但这些不能替代宿主验收。

## 10. 设计维度收敛

| 维度 | 本期结论与验证位置 |
|---|---|
| D1 定位 | 执行中有效复用与沉淀，见 §1；不以调用量为验收 |
| D2 模型状态 | 主题、事件、片段覆盖、既有 job 状态，见 §4–6 |
| D3 数据权威 | 卡片沿用现有权威；本地状态/原文保真，见 §5–6 |
| D4 分层 | 宿主语义、适配触发、MCP 共享内核；见 §3/6/7 |
| D5 接口 | memory_context 与既有 job 协议，错误/分页/版本见 §6 |
| D6 并发 | 幂等、租约、revision、同库事件对账，见 §5–6 |
| D7 失败 | 不支持/无宿主/部分输入/重试/未知结果，见 §5/7–9 |
| D8 信任 | scope 非 ACL、原文非指令、脱敏与本地默认，见 §8 |
| D9 有界性 | 分阶段预算、分页、缓存、背压，见 §4/8；默认待实测 |
| D10 观测 | 完整事件及阶段使用结果，见 §6/8 |
| D11 演进 | 增量建表、稳定协议、老工具兼容，见 §6/8 |
| D12 运维 | 本地备份、开关和回滚，见 §8–9 |
| D13 验收 | 真实宿主、独立标注、长输入尾部和恢复反例，见 §9 |
| D14 人与流程 | 宿主提炼、维护者接线、人工治理与试点标注，见 §5/9 |

设计取舍：优先任务语义节点+已证实的工具事件，优于每个工具无条件检索；优先分阶段增量总结，优于每次重扫全会话；优先复用当前 Agent，遵守既定不新增模型服务的约束。尚无需要改变用户方向的裁决；查询/预算/阈值均为可推翻默认。宿主能力与真实效果是待验证技术假设，不包装成已完成。
