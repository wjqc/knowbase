# Knowbase：Trae MCP 主线与统一知识生命周期实施计划

日期：2026-11-09。状态：方案已整理，实施待安排；未执行生产清理、迁移、配置修改或部署。

## 1. 实施基线

- Trae 是首要宿主，其他 Agent 使用同一套 MCP 契约。宿主负责理解、提炼和判断候选；Knowbase 负责检索、校验、版本、发布、证据和归档。独立执行器及向量检索都可关闭，仍能走通主链路。
- 日常任务按需检索；有明确可复用结论时，宿主可简短保存。知识服务超时、离线、积压或无法判断时，主任务可以直接完成。Stop 不强制续跑、不催办、不等模型、不要求宿主处理队列。
- 历史积压材料一次性直接清理，不为旧积压补跑模型、不开专门会话逐条提炼。以后只有明确发起的批量整理才进入宿主提炼队列；这不要求把历史积压迁过去。
- 取消按卡片类型划分的特殊治理。踩坑、决策、流程、规范、偏好、业务规则使用同一状态机、权限和证据门槛。类型保留为检索分类；来源、适用条件和例外作为内容信息。原始文档、日志与旧 `reference` 资料不批量改造成知识卡。
- 发布是本地知识进入可检索状态；Git 提交及推送是共享同步。两者分别报告。保留 SQLite、Markdown 与 Git，以及唯一固定运行包。历史 [V2 任务书](knowbase-lifecycle-v2-implementation.md) 保留作为已实施机制的参考；其按类型分流、优先 Hook 实时成卡及八关系自动识别的后续范围，以本计划为准。

## 2. 统一生命周期

所有卡使用同一条规则：**候选 → 校验与准入 → 发布为 active + once → 使用与验证 → verified、stale 或 archived**。无价值或证据不足的材料可以结算为 `no_candidate` 或待审，不必生成卡。

| 环节 | 统一规则 |
| --- | --- |
| 成卡与首次发布 | 宿主提交内容及出处或可核对的依据。内容完整、无未解决冲突、影响限于当前项目的新增或非实质补充，可在同一请求中完成校验与发布。首次发布为 `active + once`。类型不决定是否直接发布。 |
| 待审与修订 | 改变已发布结论、影响共享范围、存在冲突或来源不足，按同一规则进入待审。候选不覆盖当前发布版本；明确发现可信反证时，先按统一规则隔离旧版本。标题相似只作为复核线索。 |
| 使用与晋升 | 将检索、实际采用、任务结果和可信验证分开记账。普通反馈不投治理票。沿用 V2 证据政策：当前版本至少 3 个独立任务、2 个独立组、无未解决可信反证，才自动晋升。校验报告必须绑定执行时的卡片版本与任务身份，不能事后把旧报告挂到当前版本。 |
| 淘汰与复验 | 可信反证可让当前版本退出默认检索；支持证据被撤销后重算可信度。沿用已有归档时钟和保护条件，保留正文、修订及证据。恢复依照同一准入、复验与权限规则，不能靠改类型或回填普通好评绕过。 |
| 历史兼容 | 已发布卡保留 ID、版本和可见性；旧 staging 保持待审，进入统一复核入口；已归档卡不自动复活。先做映射报告，不批量移动文件、不重写旧证据、不把旧发布当成新一次认证。 |

首期继续使用既有受信 CLI 做人工批准和验证。普通宿主可以通过 MCP 提交和查询自己的操作结果，但不能自授审核权限、直接写状态或修改可信度。服务端复用同一发布规则，不给不同宿主或卡类型维护另一条状态机。

## 3. 实施顺序

| 任务 | 范围与主要落点 | 交付与通过条件 |
| --- | --- | --- |
| **T0 盘点并清理旧积压** | 复用 `automation/worker.py` 的盘点思路及 `jobs` 台账。以实施开始前的水位固定范围，选取未完成或已失败的旧 `capture_checkpoint/capture/extract` 材料及尚未成卡的候选。已有卡、已结算的材料关系、来源证据、版本、使用/验证记录和队列外的原始资料都保留。正在持租约或未结算写入的项目先确认结果，不能把在途写入当垃圾。 | 只读清单列出数量、原因及排除项；备份后按清单一次性撤销旧积压并清除可独立删除的正文、临时材料和候选缓存，保留最小清理回执及必要关联。二次执行不再删除；清理前后对账，已落卡和证据一致。旧材料不调模型、不进入新提炼流程。 |
| **T1 Trae 无独立模型的基线链路** | 复用 `server.py` 的 `memory_save/search/context/read/use/update` 与提炼工具。测试配置关闭独立执行器、语义索引和自动采集，使用 Trae 已接入的宿主能力。显式批量整理使用 `capture → claim → material → submit → read`，普通任务不处理积压。 | 一次真实 Trae 任务提炼并读回；第二次独立任务按项目检索并采用、反馈，再提交一处可核对的修订。另用显式批次核对分页、无候选、重放无重复落卡。记录无独立模型调用的证据。 |
| **T2 合并类型分流并修复验证绑定** | 核对 `commit_adapter.py`、`writer.py`、`versioned_feedback.py`、`knowledge_lifecycle/admission.py`、`publication.py` 及 CLI。移除以类型决定 staging、更新权限或准入的特例；按统一的内容、变更与共享风险判定。把报告与执行时的卡片版本、检查产物和真实任务绑定。 | 相同输入条件下，不同类型走同一状态转换；同一类型的正常新增和有冲突修订按同一风险规则分流。受信发布后独立读回；验证旧报告不能验证新正文、重复结果不扩票、可信反证退出默认检索、归档仍可追溯。 |
| **T3 收敛宿主流程并补恢复入口** | 更正 `docs/trae-rules.md`、MCP 初始化说明和工具描述。日常任务不被提醒领取、补材料或续租；明确整理时才提供项目内可领、到期重试及待审状态。保留幂等和租约。Hook 默认不作为主链路前置；若保留可选自动采集，修复临时 transcript 的有界持久交接，后台再解析。 | 用对照样本记录前台延迟、模型轮数和注入量。Stop 强制续跑次数、Knowbase 独立模型调用数、主任务内自动领取次数都为 0。对 MCP 不可达、库忙、模型不可用、材料过大、宿主退出后恢复分别验证；业务任务结果不受知识维护失败影响。 |
| **T4 真实验收和交付** | 先在隔离库执行 T0–T3，随后用真实 Trae 会话复验。其他 Agent 只做同一 MCP 契约的兼容冒烟。若部署，先备份、影子验证，再原地更新固定包并核对重连后的实际构建。 | 同一张样例卡贯穿生成、搜索、使用、修订和发布；使用不少于 3 个独立任务、2 个独立组验证晋升，在隔离库注入可信反证验证隔离，并用受控时钟验证归档。回执可追到卡 ID、内容版本和证据；配置、合成测试、真实宿主、部署分别标明。达不到门槛就登记失败原因，不以“入队成功”代替成卡。 |

依赖：T0 的生产动作可单独审批，不阻塞隔离工作；T1 建立基线后，T2 与 T3 可分开实施；T4 以两项结果都满足为前提。先记下关闭知识辅助时的延迟基线，再确定同设备性能阈值；不把其他宿主旧实验的耗时直接当 Trae 门槛。

## 4. 本机盘点与边界

本轮只读快照：没有待领取或待审核积压；有 **1 条失败的 `capture_checkpoint`**；提交台账中 123 条均为 `done`；索引中 260 张活跃非 reference 卡、0 张 staging。数字只是当前水位，不是执行清单；开始清理前重新按条件盘点。历史已结算的 48 条成功采集、70 条无候选采集不纳入清理。

需要优先复验的真实反例：ZCode 已在 Stop 返回后删除临时 transcript。先不把这个故障推广成 Trae 的行为，也不让修复 Hook 成为 Trae 主流程的前置。如果开启可选采集，验证宿主退出后仍能取到材料；超过预算时保留明确失败回执，不拖住主任务，也不为此引入无限量的原始会话副本。

首期不扩展独立模型、多机自动治理、八关系自动识别和实时成卡时延指标。发布安全、版本正确性和宿主不受干扰优先于卡片数量。
