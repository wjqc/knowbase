# 全员统计方案：各电脑自动上报与汇总

状态：2026-10-23 已实现采集/传输/汇总/看板/README/后台任务；本机部署与验证见实施记录，其他成员电脑尚需首次接入。用户确认只有各自电脑，无常驻统计服务器/CI；本机归属 wenjian3，成员名单会持续变化，不固定为三人。

## 本次检查结论
总体路线适合目前的运行条件。实施前补齐四项约束：动态名册与覆盖范围、epoch 恢复重叠、日统计的实际取数窗口、README 发布工作区隔离。示例预览的覆盖人数此前是一次性写入，切换统计范围会丢失；本次改为根据示例名册重算，并增加成员加入/退出模拟。

## 决策与目标
采用现有共享 Git 传输脱敏统计，客户端分别采集、上报、拉取、汇总。每个人都能在自己的卡片看板看到已上报的全员数据；共享 README 是摘要展示入口。全员覆盖必须显示“已登记人数/应登记人数、已上报人数、更新水位与缺失来源”，不以某一个客户端的数字代表全团队。

部署保持每台电脑一个 knowbase 版本，固定运行路径原地升级；统计工作目录只放 JSON、Git 元数据和汇总投影，不新增 knowbase 安装或知识权威库。

## 数据流与运行方式
1. ZCode/Claude Code/Trae 的 knowbase 操作在本机日志落库，按成员/安装/宿主记录；Hook 只做本地采集/标记待同步，不等 Git 网络。
2. 安装器登记后台任务。机器开机/登录后，在有统计变化时每 15 分钟最多上报一次；空闲只发低频心跳，避免每次工具调用产生一次 Git 提交。
3. 上报写入独立 `knowbase-stats` 分支，每台设备只更新 `devices/<installation_id>/<db_epoch>/<统计日>.json`；成员登记文件为 `members/<member_id>.json`。统计工作区与知识工作区分开，知识卡仍走原默认分支。
4. 每台电脑定期拉取统计分支，用同一 Python 内核生成团队快照和现有卡片看板。只依赖现有 Git 平台，无需一台电脑长期在线。
5. README 发布者默认是用户当前电脑，只有该角色更新默认分支 README 的标记区域。机器在线时自动刷新，其他客户端不改此区域。
6. 发布者离线时，README 保留最后更新时间；其他成员上报不受影响，各成员本地团队看板仍可更新。首版不做自动选主，避免多个发布者同时争写 README；转交角色是一次明确设置。

后台任务是产品采集组件，不启动新的 LLM。macOS 使用 LaunchAgent；其他成员的 OS 尚未核对，安装脚本按实际平台生成。关闭电脑期间不会实时上报，开机联网后补报。

## 首次接入与身份
- 每位成员仅首次安装/更新一次采集端，并确认成员 ID 与设备归属。当前用户已接入，其他电脑仍须各自完成这一步；只改当前电脑无法读取他人本地日志。
- 一个成员可绑定多台设备，同一设备上三个 Agent 共享安装 ID。成员数按已确认 member_id 去重，使用量按实际不同设备记录汇总。
- 团队名单是动态名册，不在代码、页面或配置默认值中写死三人。每位成员首次接入确认身份后登记，后续拉取自动发现新登记；改名不改变 member_id，退出记录 retired_at，不删除历史数据。
- 页面分别展示“已登记成员 N、当前已上报 X、未上报/过期/部分数据成员”；X/N 只代表已登记范围，不声称覆盖尚未接入、系统根本不知道的人。已知应接入但尚未安装的成员可预登记为 pending，不能冒充已经接入。
- 当前覆盖按当前有效名册计算；历史窗口按该窗口有效的名册及名册 revision 计算。退出成员的过去使用量仍保留，不能因为现在退出就删掉历史贡献，也不能让今天新增的成员倒填为过去的漏报。
- 不能用 Git 提交作者数、工具标签数或观测设备数代替成员数。仓库写权限和本人首次身份确认是可信文件模式的前提，不把 member_id 自报字段当作强认证。
- installation_id 不从知识 Git 复制。新机/克隆/恢复时检查设备身份，来源不明的副本隔离，防止重复累计。可信文件模式标注证据等级，不宣称中心认证。

## 上报契约
摘要 schema 建议 `knowbase.team-summary.v1`，与原 value events/metrics.v1 分开；首版采用同一统计日内的累计快照覆盖，接收方幂等替换而不是历次相加。

| 字段 | 含义与约束 |
|---|---|
| team_id / member_id / installation_id | 团队、已确认成员、设备；成员映射由登记维护 |
| schema_version / definition_version | 传输与指标定义；不兼容的记录拒绝或隔离，不混加 |
| period_start / period_end / source_timezone | 统一北京时间自然日，传输 UTC 半开区间；旧无时区日志须明确来源时区 |
| snapshot_id / sequence / db_epoch | 同设备同日更新身份和本机递增序列；旧序列不能覆盖新序列，库重建/重置不能冒充零增长 |
| generated_at / data_watermark / coverage | 生成时间、已采集到哪里、完整/部分/未知及各宿主来源 |
| command_counts / search_counts / update_counts | 聚合数值，含命令/宿主/状态；原调用参数与查询不出本机 |
| model_usage | 按宿主/来源/模型的输入、输出、缓存；缺字段用 null，订阅账户周期数据另列 |
| adoption / feedback / evolution | 采纳、反馈及自动升降级汇总；新旧协议和证据等级分开 |
| payload_hash（回执/传输元数据） | 对规范化摘要正文字节计算，放在传输/回执元数据，不作为摘要自己的字段；不能当成员认证 |

同设备/同统计日/同 epoch 只取最新有效快照，不累计历次快照。不同日期仅在定义一致且无覆盖重叠时相加。日志截断、恢复副本或计数下降时标记 partial/reset；历史证据不足则保留缺口，不猜历史全量。相同采集事件的重复导出/补报继续利用原稳定 ID 幂等。

当日快照是截至 data_watermark 的累计观测，并非提前完成一整天；显示“当前日未结束”。只有源日志连续覆盖到该水位才可标 complete，完整一日还需水位达到 period_end。source_timezone 用于解释旧无时区日志，统一展示时区不等于假定所有旧来源时区相同。

不同 epoch 的同设备/同日数据不能直接相加，也不能只按最后时间任选一份并宣称完整。按稳定 call_id/请求 ID 可重建非重叠证据时自动对账；无法证明不重叠时保留最后确认水位，将该设备该日标为 recovery_required/部分数据，不给出完整总量。epoch 改变本身不是去重证明。

新日摘要必须由实际记录按 `[period_start, period_end)` 取数，不能直接复用 overview.build 的累计输出。新调用尝试、历史 usage_log、请求用量分别保留来源与定义；缺宿主的旧记录为 unknown。命中率以命中检索数/有明细检索数重算，不能平均各成员百分比；Token 总量缺任何必要字段时只显示已观测分量及来源覆盖，不把 null 当 0。

v1 的 calls/commands 仅指新 command_calls 调用尝试；旧 usage_log 数量放 legacy_calls，不能混进新命令分布或主调用总量。首次安装前没有新日志的设备，其主调用数为未知，而不是拿历史日志替代新口径后与他人混加。

首版日摘要中的采纳/反馈/晋升/失效是回执或事件次数，不是跨日去重任务数。跨成员有效帮助率仍需原 value events 的卡版本/消费回执/任务身份链，不得从这些日计数倒推。账户周期 Token 不允许放入 v1 日请求用量列表；后续另定义账期唯一键与账户去重协议，在此之前只能独立展示，不能重复并入每天和每台设备。

首版保留所有已接受日桶，不做静默过期删除或未经定义的累计压缩；未来保留策略变更需同时定义累计基线和去重边界。协议结构见 `schemas/team-summary.v1.schema.json` 与 `schemas/team-member.v1.schema.json`；JSON Schema 只校验结构，身份、数值对账、序列及时间窗仍需程序不变式验证。

初次接入可回补该电脑仍保留的历史日志，但必须标注可观测起点、日志口径和缺失范围。旧 usage_log 与新 command_calls 不相加，旧字段缺少宿主时记 unknown。

README 表格：成员/覆盖状态、调用、命中、更新、可用 Token、统计窗口、最后上报。团队知识状态和覆盖率放表前摘要；未知、未上报、过期都明确显示。团队看板沿用当前浅色深绿卡片设计，增加成员上报摘要。设计稿 `design/team-stats-git-preview.html` 使用示例数据，非真实团队汇总。

## 防冲突、恢复与资源
- 每台设备独占自己的文件路径；本机后台发送器加锁，三个宿主不能同时写三份相同设备统计。
- 统计分支的 non-fast-forward：拉取后重放该设备快照再正常推送，有限重试。源端保留待发送状态，直到远端确认目标文件/哈希已接收才推进游标。
- 上传工作区仅检出统计分支；README 发布使用另一个专用数据工作区检出默认分支，两者分别加锁，禁止在同一目录并发 checkout 两个分支。两个目录都不包含第二套 knowbase 安装。
- README 由指定发布者单写。先读取最新默认分支，只替换标记区域；远端前进则重新拉取、重算、正常推送，最多重试3次。区域被人工改写或无法安全更新则跳过并标过期，不强制覆盖。
- 不使用 force push，不在知识写入事务里上传统计，不对主知识工作区执行统计 rebase/reset。统计任务的失败不能改写知识保存结果。
- 断网/睡眠/进程退出：保留本地待发送记录，恢复后补报；已收到旧快照的客户端不得被更晚到达的旧序列回退。
- 首版单文件上限与日桶数量有界，历史文件按明确保留策略处理；频率可配置，默认 15 分钟且无变化不提交。未来扩大团队或确需分钟级在线服务时再考虑 HTTP 汇总，当前不引入。
- 只传统计白名单。拒绝未知嵌套字段/畸形数值，不传提示词、正文、源码、凭据、本机绝对路径；输出前裁剪，不能依赖页面隐藏保护数据。

## 验收反例与边界
1. 同一台机器三个 Agent：安装数 1、成员数 1，命令按真实事件计数。
2. 一人两机：成员数 1、两机非重复实际调用可合计。
3. A=10、B=20、C未上报：已收到 2/3、观测合计 30；不能写完整全员总量。
4. 重发 A 的同一快照 10 次：仍为 10；更旧序列后到不覆盖 10。
5. 三机均有同一张卡：共享库存仍为 1，不是 3。
6. 同一周内窗外/窗内事件混合：先按实际事件/日桶时间过滤，再汇总，不能仅按周最后时间保留整桶。
7. 两台机器同时推送、README 人工编辑、发布者离线、Git 不可达：各自待发送/过期状态可见，知识卡仍可本地保存和独立同步。
8. 一成员日志恢复重置、复制他人库、计量缺失或 schema 过旧：隔离或标 partial/unknown，不伪造零或可靠身份。
9. 统计 JSON 带原文/密钥字段：导入拒绝，README/HTML 不包含该串。
10. 首轮至少三台试点设备真实安装，随后扩展到所有已登记设备，完成至少一次离线补报及跨成员汇总对账；试点设备数不是成员总数上限，模拟测试不能替代该项。
11. 成员从 N 增至 N+1：自动发现新登记，未上报分母增加，统计不出现假零；成员退出：当前名册变化、历史日桶与历史窗口名册保持。
12. 某成员一天10次命中/20次已知检索，另一成员1次命中/1次已知检索：总体命中率为11/21，不是75%。
