## 1. 定位、目标和范围

knowbase 从个人可用的记忆库，升级为能够证明自身价值的团队知识复用工具。保留原有三项目标，新增第四项：

1. 自动沉淀经验：在任务执行的有效检查点提炼，而非仅在会话结束提醒。
2. 导入并提炼知识：长输入、文档和实施方案分主题、分阶段处理，保留来源。
3. 多人共享与同步：其他成员能够收到、理解并采用正确版本的知识。
4. **知识复用价值可度量、可追溯、可展示。**

首要结果是提高有效复用，不以提高 Hook 触发次数或命令调用总量作为研发成效。

### 1.1 用户任务与完成定义

| 用户任务 | 输入与操作 | 可观察结果 | 不合格情形 |
|---|---|---|---|
| 执行中找到相关知识 | Agent 遇到新阶段、业务对象或错误 | 正确 scope、版本和状态的知识到达当前任务，必要时被采纳 | Hook 成功但模型没收到；命中错误项目；只有检索没有消费 |
| 长任务增量沉淀 | 长方案、阶段材料、代码与验证结果 | 已处理范围可追溯，新经验独立入库；允许没有可沉淀内容 | 只处理开头；分页读完即宣称提炼完成；反复保存同一经验 |
| 保存业务规则 | 需求条款、业务确认或代码逆向发现 | 条件、限制、例外、来源与版本明确，遵守待审及生效权限 | 把代码现状推断为业务真值；自动采纳待审规则 |
| 帮助另一成员 | A 的知识版本被 B 的真实任务采用 | 可还原贡献者、消费者、用途、任务结果与反馈来源 | 把两个工具当两个人；把阅读当 helpful |
| 判断推广价值 | 时间窗、成员范围、指标与对照实验 | 趋势、证据、样本量、覆盖率和限制一起展示 | 旧日志相加；满意反馈当总体效果；估算冒充实测 |

### 1.2 边界与约束

- 保持 Markdown/frontmatter 与现有 Git 知识同步路线，不借统计项目迁移知识权威。
- 保持本地 `memory.db`，其中运行记录不是可以随索引重建而丢弃的数据。
- 理解、总结、语义查重和知识提炼复用宿主 Agent；knowbase 不新增模型 API Key、模型代理或后台模型服务。
- 高频事件不进入知识 Git 仓库；统计服务不可用时，本地知识检索继续工作。
- 首版服务同一受信任团队，使用现有 PC 本地 HTML 看板；独立 Web 应用、移动端、跨组织知识保密及完整企业 BI 平台不在本期。
- 统计访问权限不改变 Git 的读权限；scope 是知识范围，不是保密 ACL。
- 首期不承诺节省比例、组织级 ROI 或固定样本数量；收益需真实测量。

## 3. 三宿主适配与能力探针（H0）

### 3.1 统一能力模型

每个实际安装实例生成 `capability_snapshot`：宿主、版本、IDE/CLI、版本形态、适配器版本、探测时间，以及下列能力的 `supported / unsupported / unknown / failed` 和证据引用：

- MCP 连通、工具许可、规则加载。
- 用户消息、工具前后、工具失败、停止、上下文压缩等事件。
- 可用的会话 ID、原生工具调用 ID、任务/提示关联标识。
- Hook 输出是否真正进入模型上下文；执行超时、输出上限与重入行为。
- 请求级或会话级输入/输出/缓存 Token、模型和成本字段。
- 数据导出或观测授权、数据粒度、是否含重复累计计数。

探测样本使用隔离材料与测试知识库，不默认修改现有会话。安装适配器时展示具体配置差异，备份原配置，不覆盖其他 Hook，不更改工具审批策略。

### 3.2 接入矩阵

| 宿主 | 基础能力及首批路径 | 用量接入 | 降级与门槛 |
|---|---|---|---|
| **Trae** | MCP 必选；按实际 IDE/CLI、个人/企业及版本探测 Hook，适配输入输出，不直接照搬 Claude 配置 | 探测可授权用量来源；企业接口仅在具备权限时使用，并核对粒度 | 无 Hook 时通过规则与显式阶段 MCP 工作流，标为辅助模式；不得宣称自动执行中接入通过 |
| **ZCode** | 复用已有工具前后、失败、用户消息及 Stop 适配；按实际版本复核 | 使用统计存在不等于可任务级导出；先核对接口和关联能力 | 无计量时仍记录知识消费；不抓取 UI 数字分摊任务 |
| **Claude Code** | MCP、Hook、会话及提示关联；独立处理输出封装和压缩事件 | 优先使用官方 OpenTelemetry；核对 provider、版本、请求及缓存语义 | 缺账号或任务关联时保持未知；安装标识不直接当成员 |

官方依据见附录 A。Trae 已有 Hook 及兼容说明，但同名事件不保证参数一致；所有支持结论均绑定实际探测版本。

### 3.3 正式路径验收

每宿主都必须从真实输入贯通到模型实际消费及知识读回，不能只验证配置文件、stdout JSON 或直接调用 Python 函数。Trae 优先取得首个完整样本，ZCode 复用现有底座，Claude 同步完成计量探针。

## 4. 执行中检索、长材料与增量沉淀（E1）

### 4.1 触发策略

| 时机 | 触发器掌握的信号 | Agent 行为 | 去重与限制 |
|---|---|---|---|
| 新任务/用户补充 | 新输入及任务标识 | 拆目标、业务对象、约束与主题，调用 `memory_context` | 不把整段长输入机械拼成一次搜索 |
| 实施方案形成/阶段切换 | 显式阶段检查点 | 按当前子任务检索标准、规则和历史决策 | 相同主题、任务版本与知识版本缓存 |
| 新模块/新业务对象 | 显式主题变化或可观察证据 | 更新主题并补检索 | 工具路径仅作线索，不靠路径推定业务语义 |
| 工具或测试失败 | 归一化错误类别、可脱敏特征 | 检索原因及已验证修复 | 排除 knowbase 自身调用，避免 Hook 递归 |
| 阶段验证完成 | 执行证据及完成标记 | 提炼经验和业务规则候选、查重、提交、读回 | 按证据及材料版本增量，不因早先一次 save 跳过后续内容 |
| 压缩/结束 | 可用的生命周期事件 | 留存游标、未完成项及待反馈项 | 不支持该事件时明确缺口，不无限 Stop 循环 |

Hook 只做确定性识别、事件归一化和有界提示。语义判断交给当前宿主 Agent；Hook 本身不启动隐式模型调用。

初始可配置预算（待试点校准，不是已验证性能）：自动检索同任务/同触发类别冷却 30 秒，每阶段最多 3 个主题查询，每次最多 3 条索引候选；提示正文最多 2 KiB，并保留可续读引用。人工或 Agent 显式搜索可在合理分页上限内继续。预算不足返回 `partial` 和未处理主题，不默默截断后宣称完整。

### 4.2 长材料处理契约

1. 输入冻结为 `material_id + source_revision/hash`；每片段有稳定定位与独立身份。
2. Agent 建立主题表：目标、子任务、业务对象、规则/约束、错误特征、未决问题，并保留来源锚点。
3. 按当前阶段优先级查询；不同阶段允许重新查询新增主题或更新知识版本。
4. 通过既有分页材料接口续读；保留已读取、已处理、已提交三个游标，不相互代替。
5. 阶段提炼走既有作业 claim/material/submit 和共享 writer，使用原幂等及租约约束，不新增旁路写文件。
6. 完成回执区分：完整、有未处理片段、无可沉淀内容、被阻断、失败。输入版本变化后不得复用旧完成结论。

输入中的指令属于待分析材料，不能覆盖宿主规则或授权。材料不可用、过大、格式不支持分别报错；超限分批，不无限展开。

### 4.3 业务规则与普通经验

- 普通经验按既有质量与治理规则保存；重复内容优先复用或修改现有卡，不按保存数量考核。
- 规则候选保存适用项目/业务域、条件、行为或限制、例外、有效范围、provenance、证据锚点、材料版本与 `code_refs`。
- 代码逆向只能证明“代码当前这样做”，不能自动证明“业务应当这样做”。业务确认、人工激活、实现验证分别记录。
- 业务规则、人员标准及需治理的偏好遵守现有 staging 与人工审核权限；本方案不扩展 Agent 直接生效权限。
- 待审、once、stale、冲突内容的递送和采纳按既有状态约束处理，不以新增观测接口绕过治理。
- 更新规则保留替代/冲突关系和历史版本；旧版本采纳与反馈不转移给新版本。

待审超期只提醒指定审核者，默认不自动通过、不阻塞普通检索。业务方决定规则真值，维护者验证结构和证据，角色可以由同一人兼任但操作权限仍区分。

## 5. 证据模型、身份与数据权威（V1/V2）

### 5.1 核心证据链

```text
A 创建/修订知识版本 → Git 同步 → B 接收该版本
    → B 的任务检索 → 实际递送/读取 → 明确采纳及用途
    → 独立任务验证结果 → 有效性反馈 → 团队指标与案例
```

每个箭头都是独立可缺失的证据，检索命中不自动补成采纳，任务成功不自动补成 helpful。

### 5.2 标识与事件公共字段

事件协议名 `knowbase.value.events.v1`，与 `knowbase.metrics.v1` 并存。

| 字段 | 约束 |
|---|---|
| `event_id`, `schema_version`, `event_type` | 事件生成即固定；本地汇总库或可选服务端按 `(team_id,event_id)` 唯一 |
| `operation_id`, `attempt_id`, `native_call_id` | 逻辑操作、执行尝试、宿主原生调用分别记录；无原生 ID 时明确缺失 |
| `installation_id`, `emitter_instance_id`, `sequence` | 安装与进程不同；恢复会话不能仅按会话+进程序号去重 |
| `host`, `host_version`, `adapter_version`, `capability_id` | 归因及解释采集边界，不能替代人员身份 |
| `member_binding_id` | 引用有来源的成员/设备确认，保留人工确认或认证绑定的证据等级；不能凭自报字段获得成员或管理权限 |
| `task_id`, `task_run_id`, `session_id`, `task_revision`, `stage` | 一项任务可跨会话/宿主；运行重试与新业务任务区分 |
| `memory_id`, `content_revision`, `context_event_id`, `use_id` | 保持既有版本及消费回执；按事件类型条件必填 |
| `outcome_id`, `feedback_source`, `evidence_ref` | 结果稳定标识、来源类别、受权限控制的证据引用 |
| `occurred_at`, `received_at` | UTC；发生与接收时间分别保存，检查时钟偏移 |
| `payload_hash`, `payload` | 规范化哈希；按事件类型白名单字段，禁止任意正文扩展 |

首批事件类型采用点分命名：`capability.snapshot`、`task.started`、`task.checkpoint`、`task.completed`、`task.abandoned`、`knowledge.created`、`knowledge.revised`、`knowledge.activated`、`retrieval.completed`、`knowledge.delivered`、`knowledge.read`、`knowledge.used`、`feedback.recorded`、`model.usage`、`collection.gap`。类型可分批启用，未启用不宣称覆盖。

查询原文不进入团队交换文件或上传内容；检索只报告主题类别/数量、结果版本及必要关联。证据正文留在允许的原系统中，汇总只保存受控引用；不可访问时显示不可复核，不复制原文绕过权限。

### 5.3 身份与归因

- 团队登记生成稳定成员标识；文件汇总模式由成员确认设备归属，保留确认来源与时间，不宣称具备中心认证强度。同一人三宿主仍为一人；可选服务上线后通过认证绑定安装实例。
- 统计显示名与真实身份映射单独授权；对外导出默认团队内匿名标识，不做个人绩效排名。
- 安装实例 ID 不进知识 Git；新安装生成新 ID。克隆统计库作为待确认来源隔离，同源事件按事件 ID 去重，发现身份碰撞须重新登记，禁止按时间窗口模糊去重。
- 卡片贡献者与内容版本建立来源账本，区分创建者、修订者、审核者；旧 Git 作者名只能是待确认线索。
- 显式继续/转交任务使用受控任务引用；无法关联则标为未关联，不按时间相近自动合并跨宿主任务。
- 多卡共同帮助一个任务，任务收益只计一次；卡片和贡献者记录贡献关系，不把一份收益复制给所有人。
- `feedback_source` 区分 Agent 声明、用户反馈、独立验证。Agent helpful 不能伪装成人工确认。

### 5.4 状态与权威

| 对象 | 权威及状态 |
|---|---|
| 知识正文、治理状态 | 现有知识流程；事件仅引用，不反向修改规则生效状态 |
| 本地业务回执 | 原消费/反馈存储；遵守已有版本、幂等和文件恢复契约 |
| 待发送事件 | `pending → leased → acknowledged`；超时重试，永久拒绝进入 `quarantined` |
| 团队原始事件 | 首版在指定汇总机的独立统计账本，事件导入幂等；可选服务接收同一协议，更正保留来源与审计 |
| 成员及安装绑定 | 首版由受控成员登记及人工归属确认维护，标注证据等级；可选认证绑定不追认旧记录为认证事实 |
| 任务结果 | 可为完成、失败、放弃、未知；验证来源另列，Agent 不能自行声明人工验收 |
| 指标与报告 | 可重建投影；绑定指标定义版本、查询范围和数据水位 |

## 6. 采集、事务与团队汇聚

```text
Trae / ZCode / Claude Code
  ├─ MCP 服务端观测
  ├─ 已探测可用的 Hook / 阶段检查点
  └─ 获授权的宿主用量适配
                 ↓
       本地规范化 + 持久事件记录
          ├─ 本机指标直接生成
          └─ 显式导出/导入 → 指定汇总机去重、关联
                                  ↓
                    授权范围的团队统计快照
                                  ↓
           knowbase dashboard → 本地 HTML 看板/周月报告

后续可选：后台上传 → 团队接收服务 → 同协议统计快照
```

### 6.1 本地写入与并发

- 在原 `memory.db` 增量新增 `value_outbox` 及必要关联表，不另建第二套知识数据库，不重置旧表。
- 采纳、版本反馈等关键事件应由对应业务事务写入 outbox；现有跨文件恢复继续以原回执/哈希为准，恢复最终成功后再生成唯一完成事件，不把预写意图当最终成功。
- 无法共享事务的知识 Git/文件动作，以既有持久回执和卡版本生成稳定投影键，由补偿器对账生成事件；不得“先改文件再尽力发一次”后声称可靠。
- 高频命令诊断可用有界缓冲和批量持久化；未落盘进程崩溃可能丢失，因此与关键业务证据分级，覆盖率不得宣称 100%。
- 复用既有锁序；SQLite 事务中不等待网络、不调用模型。后台发送先租约认领，释放事务再联网，持有效租约确认结果。
- 同一关键业务记录只能生成一个对应事件；唯一约束和稳定键兜底，不能靠 UI 不重复点击。

首版不要求后台发送器：持久记录可供显式文件导出，本机看板直接读取允许范围的记录。导出文件成功不等于汇总机已经接收，不据此把事件置为 acknowledged 或执行已确认清理；汇总机导入后生成含事件 ID/哈希的接收回执，源端显式导入并核对回执后才确认。后台上传及发送租约只在启用 S1 时接线。

建议 outbox 字段：`event_id PK, schema_version, event_type, payload_json, payload_hash, state, attempt, next_attempt_at, lease_owner, lease_until, last_error_code, created_at, acknowledged_at`。租约需 fencing/版本约束；迁移编号实施时取下一可用版本，本文不预占运行库版本号。

### 6.2 首版文件汇总与可选服务

首版不要求服务器。每位成员显式导出最小事件包，在指定汇总机导入并计算团队快照；默认 `knowbase dashboard` 仅使用本机数据，指定团队快照时才展示团队范围。文件通过团队已有授权渠道传递，本次不自动发送给其他成员。

汇总机使用独立 SQLite 分析库，默认位于知识 Git 仓库外的本机数据目录。它只保存统计证据，不是第二套知识权威；禁止把其他成员事件导入本机 `memory.db`，污染个人使用记录。显式导出/导入保留事件 ID、来源、版本、窗口、能力及归属确认；文件哈希仅校验完整性，不能认证人员。

建议表：`teams/members/installations/member_bindings`、`events`、`tasks/task_runs`、`knowledge_versions/contributor_bindings`、`usage_requests`、`metric_snapshots/report_runs`。事件按团队/事件唯一，索引团队+发生时间、任务运行、卡版本；请求用量按来源、安装实例及原生请求 ID 去重。重叠时间窗和重复导入不重复累计。

后续人数或上报频率增长时，可启用一个独立接收服务和 PostgreSQL，沿用同一事件协议与指标内核，不新增浏览器应用。服务依赖作为可选组件，不进入 MCP/看板必需依赖。没有明确自动汇聚需求前不强制建设服务器。

### 6.3 失败、有界性与恢复

以下为默认设计值，须在 H0/V1 试点验证后冻结；网络、上传及 HTTP 鉴权条目只在启用可选 S1 时适用，首版文件汇总不依赖网络：

| 边界 | 默认行为 |
|---|---|
| 单批上传 | 最多 200 事件、未压缩 1 MiB；超限拆批，单事件超限隔离 |
| 网络 | 总超时 5 秒；指数退避带抖动，最大间隔 15 分钟；不上主查询同步路径 |
| 本地待发送积压 | 100 MiB 告警；200 MiB 停止非关键诊断采样，关键记录优先保留；磁盘不足时明确降级 |
| 结果未知 | 保留原事件 ID 重传；不能生成第二个“等价”事件 |
| 部分成功 | 只确认服务端逐项持久接受/重复的事件，其余按可重试性处理 |
| 401/403 | 暂停该安装上传并提示重新授权，不无限重试，不影响知识读取 |
| 409 同 ID 不同内容 | 隔离并告警，禁止覆盖旧事件 |
| 时钟偏移/迟到 | 保留发生/接收时间；标注并按查询策略纳入迟到数据，更新报告版本 |
| 丢失量无法确定 | 显示覆盖未知或缺口时间，不能捏造丢失百分比 |

所有“可靠”承诺均以本地持久记录成功为前提；磁盘满等故障不能同时承诺零损失与零影响。观测异常优先保护知识读取，对写入证据缺口显式记录。

## 7. 接口契约（拟新增）

首版正式展示入口继续为 `knowbase dashboard [--output 文件] [--open]`，保持现有用法和默认离线行为。拟增加以下本地能力，命令参数与函数均为方案设计，尚未实现：

| 本地入口 | 输入 | 输出及语义 |
|---|---|---|
| `knowbase value export --output <事件包>` | 时间窗、成员/安装确认、允许字段 | 最小事件包及来源清单；显式执行，不自动上传 |
| `knowbase value import <事件包>` | 多成员事件包、汇总库位置、归属映射 | 按事件 ID 幂等导入；冲突隔离；未确认身份保持未知 |
| `knowbase value snapshot --output <快照>` | 汇总库、冻结时间窗及允许范围 | 最小化看板快照，含指标、授权证据摘要、版本和数据水位 |
| `knowbase dashboard --team-data <快照>` | 本地知识库、可选团队快照 | 在原看板中显示个人/团队分区；不同范围分别标注，不相加 |
| 指标及报告共享内核 | 本机只读记录或已导入团队账本 | 指标、证据摘要、周/月报告；HTML 不另计算业务口径 |

团队快照不是完整原始事件包：汇总机负责关联与计算，展示快照只带授权范围内的结果和证据摘要。解析前校验 schema、大小和类型，拒绝可执行内容及任意本地路径引用。个人汇总应使用只读数据库连接，不因生成看板隐式迁移、重建索引或写 usage。

以下 HTTP 接口仅用于后续启用团队接收服务时，统一 `/api/value/v1`，不是首版 dashboard 的依赖，也不是新站点建设任务：

| 接口 | 必要输入 | 输出及语义 |
|---|---|---|
| `POST /events:batch` | schema、批次 ID、events；认证绑定团队/安装 | 每事件 `accepted/duplicate/retryable_error/rejected`、代码、接收时间 |
| `GET /collection-status` | 时间窗、允许范围 | 来源覆盖、能力快照、延迟、积压、未关联量；未知分母保持未知 |
| `GET /metrics` | 起止、展示时区、宿主/项目/成员筛选、定义版本 | 指标值、分子分母、状态、样本量、证据等级、数据水位 |
| `GET /reuse-cases` | 同范围、分页游标 | 任务去重的证据列表及缺失环节；默认每页 50、最多 100 |
| `GET /tasks/{task_id}/evidence` | 授权任务 ID | 有权限的版本、消费、结果与反馈链；正文引用另鉴权 |
| `POST /reports` | 冻结范围、定义版本、数据水位 | 后续可选服务报告任务；首版由本地共享内核生成，不要求此接口 |

批次示例（简化结构）：

```json
{
  "schema": "knowbase.value.events.v1",
  "batch_id": "batch-example",
  "events": [{
    "event_id": "evt-example",
    "event_type": "knowledge.used",
    "operation_id": "op-example",
    "attempt_id": "attempt-example",
    "task_id": "task-example",
    "task_run_id": "run-example",
    "occurred_at": "2026-10-22T02:00:00Z",
    "payload": {
      "memory_id": "card-example",
      "content_revision": "revision-example",
      "context_event_id": "context-example",
      "use_id": "use-example",
      "state": "adopted"
    }
  }]
}
```

示例省略安装、会话等公共字段；正式 schema 按第 5 节补全。团队与成员权威取自认证及绑定，不信任客户端覆盖。

错误：400/422 畸形或不满足契约不自动重试；401/403 重新授权；409 幂等冲突隔离；413 拆批；429 遵循 Retry-After；5xx/网络错误原 ID 重传。关联事件允许乱序到达，先接收为未关联，后补关联，不伪造父事件。未知 schema 明确拒绝，不能静默忽略必需字段。

查询默认 UTC 半开区间 `[since,until)`，展示按选定时区；周起点周一。文件模式在生成和分发前裁剪授权范围，不能仅靠 HTML 隐藏成员名；可选服务模式同时执行服务端权限控制。

## 8. 指标字典与收益验证（V4/V5）

### 8.1 使用和复用

| 指标 | 定义与限制 |
|---|---|
| 命令使用明细 | 按宿主、命令列出逻辑操作、尝试、重试、成功/失败；缺稳定 ID 的历史记录另列 |
| 观测活跃成员 | 周期内有可归属事件的唯一成员；再拆仅 Hook、消费、贡献三组，不将自动触发解释成人主动使用 |
| 有效消费成员 | 至少有一次明确 referenced/adopted 的成员；不含仅命中/递送 |
| 团队覆盖率 | 有效消费成员 ÷ 同范围已确认应覆盖成员；未登记团队名单则未知 |
| 执行中检索覆盖 | 有执行阶段检索的可观测任务运行 ÷ 可观测且适用的任务运行；不冒充全部对话覆盖 |
| 采纳率 | 收到知识的任务中至少采纳一次的任务比例，按稳定 task 去重；阶段分析另按 run |
| 跨成员复用任务 | 至少采用一个已确认由其他成员贡献的卡版本的任务；身份未知单列 |
| 跨成员有效帮助率 | 明确有帮助的跨成员采纳任务 ÷ 有有效性结论的跨成员采纳任务 |
| 反馈覆盖率 | 有有效性结论的跨成员采纳任务 ÷ 符合反馈条件的跨成员采纳任务 |
| 规则效果 | 按生效规则版本统计采用、独立验证、冲突和负反馈；待审提案数量另列 |

有效性结论区分有帮助、部分帮助、无帮助及不能判断；“部分帮助”单独展示，不计入“明确有帮助”分子。“不能判断”不进入有效性结论分母，但列入已回复量；同时展示回复率和有效性反馈覆盖率。Agent 声明与人工确认分开展示。

任务内有多条相互矛盾的卡反馈时，不能取任意一条 helpful 生成任务级人工确认；任务级帮助评价优先使用独立任务反馈，否则标“卡级证据，任务结论未确认”。首版新增任务评价不反向伪造原 `memory_feedback`。

### 8.2 任务成本

记录实际请求级 `input/output/cache_read/cache_creation` 及语义版本、模型/provider、计量来源、请求与任务映射状态。各宿主缓存计入输入的方式先规范化，禁止盲加造成重复计算。

- 实际任务消耗包含范围内全部运行和重试，包含知识注入及宿主承担的提炼模型调用。
- 会话含多个任务但不能拆分请求时，只展示会话级消耗；不得按对话数或时间比例冒充任务实测。
- 请求事件与累计 counter 选择一种计量源，另一种仅对账。账单实付、provider 成本与按版本化价格估算成本分开。
- 输入/输出不同单价、缓存策略不同、订阅额度非逐请求账单等差异明确保留；不把所有 Token 统一按一个单价换算。
- 本地检索耗时、同步和服务资源成本单列，不混入模型 Token。

### 8.3 对照实验与时间效率

预先冻结任务集合、成功及质量标准、模型/provider、工具权限、知识快照、缓存与运行策略。按宿主和任务类型分层，避免将不同模型原始均值直接比较。优先使用隔离环境的配对任务或合理随机分配，避免同一人已学习答案及知识污染对照组。

对质量可比样本报告：`净节省率 = (对照消耗 - 使用 knowbase 消耗) / 对照消耗`；对照消耗为零时未定义。展示样本量、分布和不确定性，不能只报均值。失败/放弃、质量不等价及排除原因单列；同时保留所有分配任务的完成率和总成本，不通过隐藏失败制造收益。

时间拆分墙钟总耗时、Agent 执行耗时、等待时间、用户自报人工投入；后者明确估算，不用任务总耗时替代人工工时。质量通过独立验收标准、回归结果、返工/缺陷证据衡量，Agent 自评不作为独立质量结论。

样本量在基线波动可见后确定；三人首轮只证明链路和可测性，不证明普遍节省。没有对照时只报告实际消耗、重复尝试等代理指标及个案，不报告净节省。

## 9. 现有 knowbase dashboard 增强（V3）

### 9.1 视觉及体验要求

沿用 `knowbase/dashboard.py` 现有浅色、字体、配色、筛选和治理表格，不另做换肤或新增站点导航。通过同页分区或现有控件增量展示价值数据。首屏先呈现当前范围、数据质量，再呈现本期有效使用和跨成员帮助；不以累计大数字占据核心。同比/环比必须同口径且明确缺失范围，不使用装饰性动态数字或无单位趋势。

PC 以 1440px 设计，覆盖 1280px 和浏览器 200% 缩放、键盘及焦点访问；不扩展移动端。正文 14–16px，单位/样本量就近显示；颜色不作为唯一状态表达，基础对比度按 WCAG AA 检查。

### 9.2 同一看板内的分区与展示规格

| 看板分区/问题 | 内容与粒度 | 展示及交互 | 状态与验收 |
|---|---|---|---|
| 团队总览：是否持续使用 | 周活跃及消费成员、去重任务、跨成员帮助、反馈覆盖率 | 周折线看趋势；宿主条形作比较；选时间/宿主/项目后全部区域同步，点击进入同范围明细 | 首屏显示数据水位、范围、证据等级；当前周标未完结 |
| 命令与宿主：到底调用多少次 | 每命令逻辑操作、尝试/重试、状态及来源覆盖 | 可排序表格；按 Trae/ZCode/Claude 分组；展开历史独立口径 | Hook、MCP、CLI 不能不加区分相加；未知逻辑操作数不是 0 |
| 复用证据：帮助了谁 | 一行一任务，贡献者/版本/消费者/结果/来源 | 列表打开详情，按时间线展现证据链；返回保留筛选与滚动位置 | 未关联与缺证据显式展示；无权限引用不能打开正文 |
| 知识与规则：哪些值得维护 | 按卡版本的采用、负反馈、审核、过时与冲突 | 排序表格+详情，提供现有审核入口；不在看板绕过治理 | 未验证/待审有独立标识；版本切换不能继承旧验证 |
| 成本与效率：是否产生净收益 | 任务实际用量、实验组、质量和不确定性 | 实测表格、配对差异图；点击看样本及排除原因 | 无计量/无对照/样本不足分开；未测不显示节省 0% |
| 采集健康：数字能否相信 | 每安装能力、上报时间、延迟、积压、身份/任务缺口 | 状态列表及修复指引；管理员可查隔离事件原因 | 无已知分母时只显示观测缺口，不伪造覆盖百分比 |

HTML 继续内嵌生成时的数据，筛选只作用于已有快照，不能伪装成实时远程查询；需要新数据时重新运行原命令生成。默认保留现有项目筛选、标题搜索、知识治理和搜索记录，新增时间范围、宿主及个人/团队范围控件。历史治理累计值和新事件窗口指标分开展示，不能强行套用同一时间窗。

指标与趋势在 Python 共享内核计算，页面只展示与筛选，不另写口径。详情同页展开或侧栏，返回保留筛选和位置。显示生成时间、数据水位、快照范围及截断限制；无结果、零值、未知、不支持、延迟和证据不可访问分开表达。嵌入明细默认最多 500 条并标记截断，更多明细通过显式本地导出取得；后续再优化大规模场景。

无浏览器登录、Cookie、CSRF 或网页部署要求。HTML 中不能包含上传凭据、原始任务/代码，继续采用安全 JSON 嵌入和文本渲染，不执行知识正文 HTML。现有本机搜索原文只属于本地治理数据，不混入可分发团队快照；团队共享输出默认不嵌入本机原始搜索历史。静态文件无法靠前端实现访问隔离，输出时先裁剪授权范围，再依靠文件权限和受控渠道保护；已分发副本不能远程撤回，后续删除只影响重新生成结果。

### 9.3 设计交付与准入

在现有看板基础上制作增量效果稿，覆盖新增指标、命令、证据详情、成本和采集健康的关键正常及缺失状态；不制作独立站点或整站设计。以标注为模拟的数据检查长标题、负反馈及小样本。实际打开检查布局、溢出、关键联动和键盘操作，记录稿件版本与检查范围。

当前只完成文档规格，**不把本节当作高保真设计交付**。设计制作、用户评审、实现还原和真实数据验收分别记录；数据底座可先行，不因界面待评审阻塞 V1/V2。

### 9.4 周/月报告

使用相同查询内核冻结时间窗、指标版本、数据水位与生成版本。报告含活跃趋势、跨成员案例、负反馈、覆盖缺口和测量限制。迟到数据产生新版并保留旧报告标识。首版模板确定性生成，不要求模型；日后添加文字润色也不能改写数值或证据等级。

## 10. 安全、部署、迁移与回退

### 10.1 权限及保留

成员可查看授权范围内自己的任务和团队允许的汇总；团队负责人看授权汇总及案例；运维管理员管理安装、采集和服务；业务审核者沿用知识治理权限。部署前冻结具体访问矩阵，默认不开放全员任务明细。

仅在启用可选服务时配置上传凭据，绑定团队及安装、限制允许类型，支持吊销轮换；日志不记录凭据。OpenTelemetry 采用白名单字段过滤，不为计量开启完整提示词/工具参数上传。采集器不保存明文密钥和原始代码；即使卡 ID/项目标识也按团队敏感数据管理。

首版保留策略默认待部署确认：本地已确认事件保留 7 天，团队原始事件 90 天，聚合指标 12 个月；未确认事件不得因普通清理无提示删除。删除成员映射或任务证据时保留必要删除标记、重算相关投影，并使历史报告显示撤回/失效；不能凭剩余聚合恢复真实身份。备份同样受访问及保留策略控制。

### 10.2 迁移与兼容

1. 启用前记录源码/运行包/宿主版本；对原 SQLite 使用 backup API 一致备份，保留知识 Git 状态及本机配置备份，不复制活跃 WAL 库主文件冒充完整备份。
2. 在隔离副本验证增量迁移、旧卡/日志数量、旧 CLI/MCP 读取及恢复；不在本次方案交付中执行。
3. 先默认关闭新上传与自动触发，增加表、协议和能力探针；按成员/宿主开关渐进启用。
4. 旧 `usage_log`、`command_calls` 和 `metrics.v1` 保持原始口径；不补造不存在的 task/member/event，不与新独立操作总量相加。
5. 已有业务回执如需补投影，必须有确定稳定键和可确认来源；标注 `backfill`，不计入迁移后自然增长或追认人工帮助。
6. 新事件 v1 首版持续兼容；破坏性变更新增版本、明确共存窗口，在所有启用实例确认前不下线。未知版本明确拒绝。

### 10.3 部署与恢复

首版无需启动 HTTP 服务、构建前端或配置域名，安装现有 knowbase 后通过原 dashboard 命令生成 HTML。三人团队在指定汇总机保留统计账本及受控成员登记，按相同窗口导入后生成团队快照；断网不阻塞本地查看，未收到其他成员文件时标注覆盖缺口与数据日期。

后续可选服务采用内部接收服务+PostgreSQL，经组织已有 TLS/认证入口访问，无网页静态资源部署。指定汇总机/服务每日备份，RPO 24 小时/RTO 4 小时为待演练运维目标；演练后才能宣称满足。恢复后重新导入保留的事件包或补传，缺失范围明确披露。

回退顺序：关闭新自动触发及上传 → 保留待发送记录和证据 → 切回已验证兼容包/配置 → 核对旧检索和写入。优先仅回代码、保留新增表；若旧版不兼容迁移后的库，先导出新增资产并停止相关写入，再按验证过的恢复流程操作，禁止直接覆盖正在写入的业务库或删库重建。

## 12. 验证样本、反例与最终验收

### 12.1 风险优先贯通样本

三位真实成员 A/B/C，不是三个工具标签。使用各自安装实例和正常宿主许可，准备独立人工预期：至少包含两个阶段的真实任务、长材料后半段的关键规则、一个例外、一次错误及解决证据。冻结材料版本，预先由业务审核者确认应识别/不应生效的内容。

1. A 从任务中沉淀经验与业务规则候选，读回来源/版本；规则经已有人工流程生效。
2. B 在另一机器、不同宿主执行相关任务；记录接收端版本、新鲜度、阶段检索及实际采纳。
3. 验证 B 的任务结果，分别收集 Agent 声明与用户反馈；看板能还原证据链。
4. C 使用第三宿主验证复用或发现失效；修订后的版本不继承旧有效性。
5. 三宿主均至少一条真实完整任务链；这是接线门槛，不是收益样本量。

### 12.2 必测反例

| 编号 | 场景 | 独立预期 |
|---|---|---|
| T01 | 同事件重传、同操作多次执行 | 一条事件、一个逻辑操作；尝试数单列 |
| T02 | 断网/响应丢失/部分成功 | 原 ID 补传，已接收项不重复，其他项可恢复 |

| T14 | 团队快照夹带本机原始查询、未授权任务或密钥 | 生成/导出前拒绝或裁剪；不能靠 HTML 隐藏；可选服务另测跨团队拒绝 |
