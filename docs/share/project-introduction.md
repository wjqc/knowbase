# 薪火 knowbase 项目介绍

> 部门内部分享版｜2026-10-22  
> 面向研发、测试、架构及 AI 工具使用者。本文按当前工作区 `0.2.0rc5` 源码整理；实际安装包、宿主接线和验收进度可能不同，须以运行版本及真实任务验证为准。

## 1. 一句话介绍

**薪火是一个供 AI Agent 共用的经验记忆库：把工作中验证过的排查方法、技术决策、操作流程和业务规则整理成经验卡，让后续任务能找到、核对并复用。**

个人使用时，它让不同 AI 工具共用一份经验；团队使用时，每位成员通过内网 Git 共享知识卡，在各自机器上检索。

“一个人的坑，成为团队可以复用的经验”，是项目希望实现的价值。能否减少重复排查，需要在真实任务中持续验证。

## 2. 为什么需要它

我们已经在使用 AI 编程，但经验往往留在一次对话里。

| 日常问题 | 对工作的影响 | 薪火的处理方式 |
|---|---|---|
| 同一个报错换个会话又重新排查 | 重复分析相同原因 | 保存问题、适用条件、处理动作和验证证据，下次先查 |
| Claude Code、ZCode、Trae 各自保留上下文 | 切换工具后经验难以接续 | 通过统一 MCP 工具访问同一份本地经验库 |
| 同事已经解决的问题，其他人不知道 | 团队反复试错 | 通过内网 Git 同步经验卡，各机建立本地索引 |
| 经验过时，但 AI 仍照旧执行 | 错误建议反复出现 | 按知识版本绑定反馈，失效条目退出默认检索 |
| 原始资料很多，真正的结论难找 | 文档越多，上下文越拥挤 | 原始材料保真留存，可复用结论单独成卡 |

适合沉淀的内容包括：环境兼容问题的排查方法、接口使用的前置条件、重复操作的固定步骤、架构选择的原因，以及有明确出处的业务规则。

一次性进度、测试通过的总数、能直接从仓库查到的文件清单，不必全部记成经验卡。

## 3. 一条经验如何被复用

以“某接口升级后，旧客户端仍发送秒级时间戳，导致验签失败”为例。以下是说明性场景，具体单位必须以真实接口契约为准。

1. **解决问题并留下证据。** 核对接口版本、请求样本和签名规范，确认问题原因与修复结果。
2. **提炼成卡。** 说明什么版本需要毫秒级时间戳、旧版接口是否适用，以及如何验证请求。
3. **先查重再保存。** 已有同一主题的卡就补充原卡；新结论再保存，并记录来源与版本。
4. **共享到其他成员。** 本地保存、Git 提交、远端推送和同事拉取分别有自己的结果。
5. **在下一次任务中检索。** Agent 按当前项目和报错查询，读卡并核对适用条件。
6. **实际使用后反馈。** 只有完成了任务验证，才能报告“有帮助”“不适用”或“已经失效”。

检索命中、阅读、采纳和验证成功，是四件不同的事。薪火分别记录它们，避免把“被看到”当成“有效”。

## 4. 经验卡里写什么

新卡统一包含八项内容。它们的目的，是让没有参加原始讨论的人也能判断该不该用。

| 小节 | 要回答的问题 |
|---|---|
| 结论 | 下次遇到相同问题，应记住什么？ |
| 解决的问题 | 当时的现象与影响是什么？ |
| 适用条件 | 哪个系统、版本、状态或前提下有效？ |
| 不适用条件 | 有哪些例外，什么时候不能照做？ |
| 可执行动作 | 使用者具体要检查或执行什么？ |
| 关键证据 | 哪个输入、输出、条款或代码位置支持结论？ |
| 验证情况 | 在什么环境下，用什么方法验证到了哪一步？ |
| 未知与待确认 | 还有什么没有确认？ |

知识类型包括踩坑 `pitfall`、决策 `decision`、流程 `workflow`、标准 `standard`、偏好 `preference` 和业务规则 `bizrule`。

“测试通过”不能替代验证说明，“参见某文档”不能替代关键证据。经验卡需要写出足以复用的结论，同时保留可追溯来源。

## 5. 任务中怎么用

### 5.1 开始前查一次，执行中按主题补查

短任务可以从 `memory_search` 开始：用项目名、具体技术词或报错特征检索，再用 `memory_read` 读全文。

长任务则按阶段调用 `memory_context`：拆解需求后、进入新子任务时、遇到新错误时、做重要决策前，都可以提交当前主题与短查询。系统按预算返回候选与未完成项，避免长方案只在开场检索一次。

项目范围由显式 `scope` 或目录映射确定；默认检索当前项目和 `global` 通用经验。无法确认项目时，不应把其他项目经验混进来。

### 5.2 保存的是结论，原始材料另存

原始文档、日志、代码和导入文本保存在 source 层，保留内容快照与来源信息。默认检索面向经验卡，source 不直接混入结果。

短结论可通过 `memory_save` 保存。长材料可进入提炼队列：领取批次、分页读取、检查相似卡，再提交候选。提炼使用当前宿主的模型，knowbase 内核不另建一套模型调用服务。

任务入队只表示材料已登记；最终要读回实际卡片 ID、内容版本和保存状态，才能确认成卡。

### 5.3 反馈绑定具体版本和任务

`memory_use` 记录参考、采纳、无关或待验证；`memory_feedback` 记录任务验证结果，并绑定知识版本、使用回执和稳定任务结果 ID。

同一任务重复提交不应重复累计证据。正文更新后，旧版本的验证不能自动证明新版本有效。

## 6. 为什么能让多个工具共用

MCP 可以理解为 AI 工具调用外部能力的统一接口。各宿主通过标准输入输出启动本地 knowbase 服务，调用同一组检索、读写和反馈工具。

```mermaid
flowchart LR
    A[Claude Code / ZCode / Trae 等宿主] --> B[本地 MCP / Hook]
    B --> C[knowbase 检索、写入与治理]
    C --> D[Markdown 经验卡与 source]
    C --> E[本机 SQLite 索引与运行记录]
    D <-->|知识文件同步| F[内网 Git 共享仓]
    F <-->|各机同步| G[同事的本地经验库]
```

关键技术选择如下。

| 技术 | 在项目中承担的职责 | 对使用者的意义 |
|---|---|---|
| Markdown + frontmatter | 保存卡片正文、类型、范围和治理信息 | 内容可读、可迁移、可审查 |
| Git | 记录知识变更，支持各机共享 | 可以追踪修改并处理版本冲突 |
| SQLite FTS5 | 本地全文检索与结构化记录 | 不需要单独部署数据库服务 |
| 字符 n-gram 向量、RRF 融合 | 补充字面模糊召回，融合候选名次 | 降低完全依赖原词匹配的限制 |
| MCP | 向不同 AI 宿主提供统一工具 | 接入不绑定某一家模型 |
| Hook | 在宿主事件发生时提醒、检索或观察 | 减少完全依靠模型主动记忆的遗漏 |

当前向量实现是字符特征方案，不等于通用语义理解；同义改写、业务歧义仍需人工和任务验证。

Markdown 是知识内容的唯一真相；SQLite 同时包含可重建索引和不可从 Markdown 恢复的本地运行记录。因此，“索引可重建”不代表可以随意删除数据库。

## 7. AI、服务端与人的分工

| 参与方 | 负责什么 |
|---|---|
| 宿主 Agent | 判断相关性、核对条件、执行任务、提炼结论、报告验证结果 |
| knowbase 服务端 | 校验结构、查重、控制写入、绑定版本与回执、执行确定性治理策略 |
| 人与团队维护者 | 确认业务来源、处理标准和偏好提案、裁决争议、管理共享仓和发布版本 |

标准和偏好由 Agent 提案后进入 `staging` 待审核；Agent 不能直接改写已生效的治理规则。

业务规则也先进入候选区。当前源码支持按版本验证后的自动激活：默认要求至少 **3 个独立已完成任务、2 个会话的正向证据**，有出处且不存在当前版本的负面冲突。也保留人工激活通道。是否启用由配置决定，旧运行包可能没有这项能力。

当前自动策略中，两个独立任务的 `not_helpful`，或一条版本绑定的 `incorrect` / `outdated`，可使知识进入 `stale` 并退出默认检索。工具标签仅用于归因，不等于真实人员身份；自动验证记录也不能替代业务方签字确认。

## 8. 团队接入后，各自保存什么

每位成员都在本机运行服务。共享的是知识文件，日常读取使用本机索引；Git 同步失败时，本地已保存内容不会因此被撤销，但同事可能尚未收到。

- **共享层：** 经验卡、治理提案，以及按团队约定纳入共享仓的 source 材料。
- **本机层：** 配置、索引、使用回执、会话观察、统计日志和备份。
- **汇总层：** 显式导出、接收并核对后的最小价值事件，用于团队统计。

程序代码仓与经验数据仓是两个仓库。经验数据只使用批准的内网远端；当前远端白名单需要由维护者按实际地址核对。

“本地服务”描述的是 knowbase 的存储和执行位置。Agent 读到的经验可能进入宿主模型上下文，使用什么模型、允许处理什么材料，仍按部门的数据使用要求执行。

## 9. 怎么判断有没有价值

离线 HTML 看板展示调用、知识状态、命中、更新、Token 用量和自动演进的汇总卡片。团队汇总通过显式导出、导入和回执核对完成。

分享时建议分三个层次看数据：

| 层次 | 关注的问题 | 不能直接推出什么 |
|---|---|---|
| 使用情况 | 有多少调用、命中和知识更新？ | 命中不等于采纳 |
| 有效复用 | 哪些任务实际使用，并验证有效？ | 工具来源数不等于人数 |
| 净收益 | 相比不用经验库，是否减少时间、Token 或遗漏？ | 没有对照时，不能报节省百分比 |

当前源码的请求级用量采集支持 Claude 本地 transcript；ZCode、Trae 的对应采集入口明确返回不支持，不估算填充。缺失数据应显示未知。

## 10. 当前做到哪一步

截至本文日期，应把源码能力与真实使用证据分开介绍。

| 范围 | 当前可确认的情况 | 分享口径 |
|---|---|---|
| 核心实现 | 当前源码注册 16 个 MCP 工具，包含检索、写入、执行中上下文、提炼、使用和统计接口 | 具备本地实现，运行服务需核对版本 |
| ZCode | 已有受控任务中的执行中注入与消费证据，以及有界材料提炼样本 | 已有局部真实证据，完整验收仍有待办 |
| Claude Code | 已有 MCP / Hook 注册记录和本地请求用量来源 | 配置注册不能替代真实消费验收 |
| Trae | MCP 已接线；当前源码有 Hook 适配与本地测试 | 真实整链未验收前按主动调用的辅助模式介绍 |
| 业务规则自动演进 | 当前源码具备版本绑定验证与自动激活、淘汰策略 | 不代表所有已运行的固定包都已升级 |
| 跨成员与净收益 | 已有协议、汇总实现及本地验证材料 | 三位真实成员复用、净效果对照仍待验收 |

上述进度依据仓库内的能力记录和验收文件，本次文档编写未重新执行各宿主真实任务。现有历史分享稿中“三段式卡片”“所有规则必须人工激活”等表述，已不能完整代表当前源码。

## 11. 建议的部门试点

先选择一个真实项目，邀请三位使用不同宿主的同事参与，由一位维护者提供固定安装包、内网数据仓和统一 scope。

1. A 解决一个有复用价值的问题，保存经验并确认已同步。
2. B 在另一台机器的真实任务中检索、核对并使用，记录任务结果。
3. C 遇到边界条件或版本变化，补充证据，检查旧反馈是否正确隔离。
4. 对照不用经验库的过程，记录额外检索成本、遗漏和实际收益。

这条试点链既检验“知识能不能传过去”，也检验“传过去以后是否真的帮到工作”。

## 12. 分享顺序与现场演示

建议控制在 15～20 分钟：

| 时间 | 内容 |
|---|---|
| 3 分钟 | 重复排查、切换工具、同事经验不可见三个场景 |
| 4 分钟 | 一张经验卡的八项内容与复用流程 |
| 4 分钟 | MCP、本地索引、Git 共享及反馈治理 |
| 5 分钟 | 隔离库现场演示：保存 → 检索 → 读回 → 记录使用和结果 |
| 3 分钟 | 当前边界与三人试点安排 |

演示使用专门的测试库，从空库开始；不要依赖维护者已有卡片编号。先跑通《[项目接入文档](integration-guide.md)》的首次验收，再按现场时间决定是否展示跨机同步。
